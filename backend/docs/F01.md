A validação anterior verificava apenas o prefixo da URL. Foram reproduzidas configurações aceitas indevidamente sem servidor, sem database ou com porta inválida.

Agora a URL é interpretada pelo SQLAlchemy antes de montar uma conexão. Ela exige driver `mysql+pymysql`, servidor e nome do database explícitos; uma porta informada deve estar entre 1 e 65535. Omitir a porta mantém o padrão MySQL 3306. Outros drivers, URL ausente e configurações incompletas são recusados, sem fallback para banco local.

Os controles existentes de TLS e timeout permanecem em variáveis próprias: parâmetros da URL não podem desativá-los ou substituí-los. Variáveis exportadas no processo continuam tendo precedência sobre `.env`. Mensagens de validação omitem os valores de entrada, e `get_settings()` mantém o erro público sanitizado.

O novo teste de startup impede conexões SQLAlchemy e chamadas ao bootstrap administrativo enquanto inicializa o ciclo de vida ASGI, abre Swagger/OpenAPI e verifica uma requisição sem token. A inicialização não tenta criar contas, conectar ao banco ou carregar seeds.

### Sessões e transações

Os novos testes de [`test_transactions.py`](../tests/integration/test_transactions.py) executaram SQL real no database descartável `prontuario_test` e confirmaram:

- `session()` com `commit()` persiste os dados, visíveis por outra conexão.
- Fechar uma sessão após `flush()`, sem commit, desfaz os dados enviados ao banco; outra conexão não vê a gravação pendente.
- `session()` com `db.begin()` desfaz a unidade inteira quando ocorre uma exceção, incluindo permissão e auditoria da operação.
- Uma violação de unicidade não deixa gravações parciais. Após `rollback()`, a mesma sessão pode ser reutilizada para uma operação válida.
- `engine().begin()` confirma todas as gravações quando termina normalmente e desfaz todas quando ocorre uma exceção.
- As sessões e conexões usadas pelos testes são devolvidas ao pool ao sair dos contextos, inclusive nos caminhos de erro.

O contexto `with session() as db` fecha a sessão; ele **não confirma gravações automaticamente**. Use `db.commit()` explicitamente ou delimite a unidade com `with db.begin()`. Se capturar uma falha de flush e continuar com a mesma sessão, execute `db.rollback()` antes de reutilizá-la. A falha deve continuar sendo propagada/tratada, sem responder sucesso antes do commit.

### Contratos e validação

- Login, refresh e troca de senha recusam campos desconhecidos e limitam os tamanhos de entrada. O formulário de login passou a ser validado por `LoginRequest`; o OpenAPI usa o schema desse mesmo DTO, evitando manter uma descrição independente dos campos.
- O login exige grant, usuário e senha; aceita os campos de cliente do Swagger somente vazios. Campos repetidos, estrutura inválida e UTF-8 inválido retornam 400; tipo de conteúdo incompatível retorna 415. O tipo de conteúdo é comparado sem distinguir maiúsculas/minúsculas.
- JSON inválido, propriedade extra ou tipo/tamanho inválido nas entradas JSON retorna 422 antes da operação. Credencial de formato válido, mas incorreta, continua retornando 401. Os clientes devem considerar a distinção entre erro de formulário e erro de autenticação.
- Os IDs públicos são UUIDs serializados como strings. A saúde bem-sucedida usa somente `ok`, e a expiração do token deve ser positiva. Campos privados são filtrados pelos contratos de resposta.

### Erros

Handlers e middleware usam a mesma função `views/errors.py::error_body` para produzir `ErrorResponse`, preservando os códigos existentes. O request ID é um UUID correspondente ao header, com mensagem pública opcional. Entradas inválidas, detalhes HTTP não textuais e respostas do servidor fora do contrato não expõem senhas, tokens, dados recebidos ou exceções ao cliente.

Os testes também confirmaram a preservação dos controles HTTP existentes. Rejeições anteriores às rotas, como gateway/host/CORS, mantêm os limites descritos em `CONTRATOS.md`; não são confundidas com o envelope dos erros da aplicação.

### Paginação

[`views/pagination.py`](../src/prontuario_backend/views/pagination.py) define `PaginationParams` com limit padrão 20 (1 a 100) e offset padrão 0 (0 a 100.000). Entradas inválidas recebem 422. `PageResponse[ItemResponse]` contém `items`, `total`, `limit` e `offset`, filtra os campos dos itens e recusa contagens inconsistentes.

Futuras listagens devem usar os mesmos filtros/permissões na consulta e no total, com ordenação estável e leitura consistente. Os Models recebem os parâmetros validados pelo Controller, sem importar Views. Uma página vazia continua sendo sucesso 200. Não foi criado endpoint de listagem nesta etapa; rotas de paginação existem somente nas aplicações temporárias dos testes.
